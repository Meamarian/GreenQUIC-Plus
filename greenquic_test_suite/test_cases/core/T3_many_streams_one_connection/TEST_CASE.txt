T3 — Many streams inside one QUIC connection
============================================

Category:
    core

Purpose:
    Prove that many QUIC streams do not create many RSS flows or automatically activate multiple DPDK lcores.

Object relationships:
Connection:
    1 QUIC connection.

Stream:
    Many simultaneous streams inside the same connection.

UDP/RSS flow:
    1 UDP flow. Stream IDs are encrypted/encoded inside QUIC and are not visible to normal NIC RSS.

DPDK lcore:
    One main DPDK lcore handles the UDP flow.

MsQuic partition:
    One MsQuic partition owns the connection; all streams share it.

Important ownership correction:
    MsQuic decides which partition owns a connection.
    RSS/NIC decides which RX queue/lcore receives a UDP flow.
    GreenQUIC configuration maps partition -> DPDK lcore only for hints.
    This mapping does not force RSS to select the same lcore.

Mapping used by the generated default configuration:
Single-queue configuration used by this testcase:
    SERVER: DPDK lcore 8; P0/P1/P2/P3 hints all map to lcore 8.
    CLIENT: DPDK lcore 12; P0/P1/P2/P3 hints all map to lcore 12.
    MsQuic still has four configured worker CPUs/partitions on each endpoint.

Diagram:
                              CLIENT                                      SERVER
                              |                                             |

                              |                                             |
                              |<------- multiplexed stream data ------------|
                              |--- ACKs for same connection --------------->|

Signals expected:
    One lcore sees most RX/TX pressure; one partition generates ACK/CUBIC hints; transfer hint remains active while streams are receiving/sending.

Energy management during ACTIVE periods:
    The one active lcore may run at freq_up/max because multiplexed stream traffic raises one flow's pressure.

Energy management during IDLE periods:
    Idle behavior appears only after all streams complete or if the stream group itself contains gaps.

Expected energy result:
    Low to medium. The testcase is primarily a topology and correctness test.

What to measure:
    * total package joules and average package power on both endpoints;
    * elapsed time, throughput and joules per GB/request;
    * per-lcore frequency residency and C-state residency;
    * RX/TX bursts, empty pulls, queue/ring pressure and EWMA pressure;
    * selected GreenQUIC action, total sleep requests and hint timeline;
    * QUIC RTT, ACK delay, retransmissions, recovery interval and completion time.

Limitations and interpretation:
    The stock quicinterop client sends the configured URL list as multiple streams on one connection. It does not create controlled gaps between those streams.

Do not change useful work between OFF, BASIC and PLUS. Keep payload size, repetitions,
source-port strategy, CPU pinning, server temperature and network conditions constant.

Final V18 policy expectations
-----------------------------
* Each lcore updates only the physical signals for directions it owns.
* RX and TX remain separate until the final per-lcore max action.
* Queue/ring backlog should dominate when parallel work exceeds service capacity.
* Save and compare both dpdk.ini and powermng.ini hashes for every run.
