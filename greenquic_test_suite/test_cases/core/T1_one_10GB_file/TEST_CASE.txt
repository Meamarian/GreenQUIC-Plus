T1 — One continuous 10 GB file
==============================

Category:
    core

Purpose:
    Prove that GreenQUIC does not damage a large continuous transfer and does not downscale when the datapath genuinely needs capacity.

Important ownership correction:
    MsQuic decides which partition owns a connection.
    RSS/NIC decides which RX queue/lcore receives a UDP flow.
    GreenQUIC configuration maps partition -> DPDK lcore only for hints.
    This mapping does not force RSS to select the same lcore.

Mapping used by the generated default configuration:

    CLIENT: DPDK lcore 12; P0/P1/P2/P3 hints all map to lcore 12.
    MsQuic still has four configured worker CPUs/partitions on each endpoint.

Signals expected:
    SERVER_FILE_TX_ACTIVE, CLIENT_FILE_RX_ACTIVE, active RX/TX bursts, ACK_PENDING, possible CUBIC_RAMPING/CWND_BLOCKED, and CUBIC_RECOVERY only after loss.

Energy management during ACTIVE periods:
    RX/TX pressure keeps the active lcore at keep/freq_up/freq_max. CUBIC recovery may force short urgent protection. TX backlog must always prevent sleep.

Energy management during IDLE periods:
    There should be almost no true idle interval during the transfer. Pause/freq_min/sleep should be rare. No energy saving is expected if line rate requires maximum processing.

Expected energy result:
    Low to medium saving. The important result is unchanged throughput and completion time, with no false downscale.

What to measure:
    * total package joules and average package power on both endpoints;
    * elapsed time, throughput and joules per GB/request;
    * per-lcore frequency residency and C-state residency;
    * RX/TX bursts, empty pulls, queue/ring pressure and EWMA pressure;
    * selected GreenQUIC action, total sleep requests and hint timeline;
    * QUIC RTT, ACK delay, retransmissions, recovery interval and completion time.

Limitations and interpretation:
    The 10 GiB source is opt-in to avoid unexpected disk use. Create it with common/bin/prepare_assets.py --common common --create-10g. It is sparse where supported; add --materialize only for storage-sensitive runs.

Do not change useful work between OFF, BASIC and PLUS. Keep payload size, repetitions,
source-port strategy, CPU pinning, server temperature and network conditions constant.

Final V18 policy expectations
-----------------------------
* RX burst, RX queue, TX burst, and TX ring are recorded independently.
* QUIC floors are applied after physical smoothing.
* Final lcore action is the maximum of owned directional controls, never a sum and never another EWMA.
* Save and compare both dpdk.ini and powermng.ini hashes for every run.
