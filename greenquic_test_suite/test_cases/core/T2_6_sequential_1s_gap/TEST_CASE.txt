T2_6 — Sequential connections with 1s gap
=========================================

Category:
    core

Purpose:
    Measure the pause/frequency/sleep transition for a 1000000 microsecond inter-connection gap.

Requested server paths:

Object relationships:
Connection:
    Many connections over time; exactly one active connection at a time.

Stream:
    One stream per connection.

UDP/RSS flow:
    One active UDP flow at a time; each new connection may hash differently.

DPDK lcore:
    One active lcore at a time; lcore identity can change across repetitions.

MsQuic partition:
    One active partition at a time; partition identity can change across repetitions.

Important ownership correction:
    MsQuic decides which partition owns a connection.
    RSS/NIC decides which RX queue/lcore receives a UDP flow.
    GreenQUIC configuration maps partition -> DPDK lcore only for hints.
    This mapping does not force RSS to select the same lcore.

Mapping used by the generated default configuration:
Single-queue configuration used by this testcase:
    SERVER: DPDK lcore 8; P0/P1/P2/P3 hints all map to lcore 8.
    CLIENT: DPDK lcore 12; P0/P1/P2/P3 hints all map to lcore 12.
    MsQuic still has four configured worker CPUs/partitions on each endpoint.

Signals expected:
    Active: transfer hints, bursts, ACK and CUBIC events. Gap: zero bursts, TX ring empty, transient hints expire and consecutive empty-pull counters increase.

Energy management during ACTIVE periods:
    At connection/chunk start, frequency is retained or increased. Hard max is reserved for real queue/backlog or recovery pressure.

Energy management during IDLE periods:
    Longest idle residency; check next-request wake-up latency carefully.

Expected energy result:
    Very high, possibly highest

What to measure:
    * total package joules and average package power on both endpoints;
    * elapsed time, throughput and joules per GB/request;
    * per-lcore frequency residency and C-state residency;
    * RX/TX bursts, empty pulls, queue/ring pressure and EWMA pressure;
    * selected GreenQUIC action, total sleep requests and hint timeline;
    * QUIC RTT, ACK delay, retransmissions, recovery interval and completion time.

Limitations and interpretation:
    The configured wait starts after the previous client process exits. Process startup adds a small amount to the next observed connection gap.

IN-PROCESS CLIENT REQUIREMENT:
    A valid two-sided GreenQUIC energy run requires INPROCESS_CLIENT_BIN.
    It keeps one MsQuic/DPDK process alive across all connections/batches.
    --approximate launches stock client processes and is not a valid client-side
    empty-poll/DVFS measurement. For sequential tests it can still exercise the
    persistent server; for parallel tests it is only a server-load approximation.

Do not change useful work between OFF, BASIC and PLUS. Keep payload size, repetitions,
source-port strategy, CPU pinning, server temperature and network conditions constant.

Final V18 policy expectations
-----------------------------
* Burst EWMAs react quickly at each chunk/connection.
* Queue/ring EWMAs retain backlog evidence through short gaps but decay across real idle.
* Semantic floors expire independently and never enter the four physical EWMAs.
* Save and compare both dpdk.ini and powermng.ini hashes for every run.
