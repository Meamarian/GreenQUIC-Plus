Optional exact in-process client interface
==========================================

The stock quicinterop executable creates one connection per process invocation.
That is not a valid two-sided GreenQUIC T2/T4 runner: sequential invocations tear
client DPDK down between gaps, while parallel invocations create competing EAL
instances for the same NIC. The in-process client is therefore required for valid
client and server energy-management measurements.

Set INPROCESS_CLIENT_BIN to an executable supporting:

  client --server HOST --port PORT \
         --workload sequential_connections|parallel_connections \
         --gap-us N --repetitions N --parallel N \
         --download-dir DIR --path /a --path /b ...

It must:
  * remain in one process for all repetitions;
  * create/close connections according to the selected workload;
  * start the configured gap after the previous connection/batch completes;
  * return nonzero on any failed transfer;
  * preferably log actual completion/start timestamps;
  * use the same patched MsQuic library and role-specific dpdk.ini.

Without this helper, --approximate is limited to exploratory/server-side load
creation. Do not report its client-side empty-poll, DVFS, sleep, lcore or partition
results as the intended testcase.
